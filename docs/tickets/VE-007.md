## Description

Provision the Auth & Pairing, Ingestion, Alert-Rule Engine, Notification, and Reporting/Export services as independent containers (Docker/Kubernetes), decoupling ingestion load from dashboard latency, connected via a managed message queue (SQS/PubSub).

### Architecture Decisions

#### Containerization

All services containerized with Docker:

```dockerfile
# Example: auth-pairing/Dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base
WORKDIR /app
EXPOSE 8080
# ... (multi-stage build)
```

#### Message Queue

**Dev environment:** Redis (stand-in for SQS/PubSub)  
**Production:** Managed queue (AWS SQS / Google PubSub / Azure Service Bus)

**Event flow:**
1. Companion app → Ingestion Service → PostgreSQL (durable write)
2. Ingestion Service → Redis queue (event notification)
3. Alert Engine ← Redis queue (consumes events)

This decouples ingestion throughput from alert evaluation.

#### Database Connection

All services share PostgreSQL instance but can scale independently:

```
postgres (TimescaleDB container)
├── auth-pairing → writes to: accounts, attestations, pairing_sessions, devices, refresh_tokens
├── ingestion → writes to: events
└── alert-engine → reads from: events, alert_rules
```

## Test Plan


   - Verify health endpoints respond

   - Verify dashboard can still read data

   - Verify alert engine can consume
