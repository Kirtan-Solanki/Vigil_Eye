# VE-003: Ship v1 Messaging as Metadata-Only; Gate Content Capture

**Ticket ID:** VE-003  
**Epic:** EPIC 0 — Phase 0 (Blocking)  
**Priority:** Critical  
**Type:** Security / Compliance  
**Status:** ✅ COMPLETE

---

## Source

- **Security Assessment Risk R-2 (Critical):** SMS 'content' capture legally fraught
- **TRD §6:** Data model already allows metadata-only approach

---

## Description

Per the Security Assessment Risk Register, SMS 'content' capture under the keyword watch-list feature is legally fraught: most jurisdictions require all-party consent and a minor's consent typically cannot satisfy that.

**Solution:** Ship v1 with sender/recipient/timestamp metadata only (as the TRD's own scope already allows), and place content capture behind a separate, later, explicitly-disclosed phase pending legal sign-off (VE-001).

**Non-negotiable invariant #3:** This is not a "nice to have" — it's a hard gate to prevent stalkerware classification and legal liability.

---

## Acceptance Criteria

- [x] v1 SMS alert rules operate on metadata fields only (sender, recipient, timestamp) — no message body is stored or evaluated
- [x] Keyword-flag alerting is either removed from v1 scope or reworked to metadata-only signals
- [x] A distinct, flagged backlog item exists for future content-capture work, blocked on legal sign-off
- [x] No `content` or `body` field exists in the Event data model for `SmsMeta` type events

```csharp
public class Event
{
    public enum EventType
    {
        Call = 1,
        SmsMeta = 2,           // Metadata only: sender, recipient, timestamp
        Location = 3,
        AppUsage = 4,
        WebHistory = 5,
        DeviceStatus = 6,
        TamperDetected = 7
    }
    
    // No separate 'content' field exists in schema
    // Payload is encrypted and validated at ingestion

```

### API Validation

**File:** `backend/ingestion/Controllers/EventsController.cs`

```csharp
// VE-003: Validate that SMS events contain only metadata (no content field)
if (eventData.Type == "sms_meta")
{
    var payload = JsonSerializer.Deserialize<Dictionary<string, object>>(eventData.Payload);
    if (payload != null && payload.ContainsKey("content"))
    {
        _logger.LogWarning(
            "VE-003: Rejected SMS event from device {DeviceId} — content field present in v1 (metadata-only)",
            deviceId);
        return BadRequest(new {
            error = "invalid_event",
            message = "SMS events must be metadata-only in v1 (sender, recipient, timestamp). Content capture is feature-gated."
        });
    }
}
```

**Enforcement:** The ingestion API actively rejects any SMS event containing a `content` field.

### Metadata-Only SMS Event Schema (v1)

```json
{
  "type": "sms_meta",
  "payload": {
    "sender": "+1234567890",
    "recipient": "+0987654321",
    "timestamp": "2026-09-13T12:34:56Z",
    "direction": "incoming"
  },
  "occurred_at": "2026-09-13T12:34:56Z"
}
```

**Explicitly excluded from v1:**
- `content`: message body text
- `keyword_matches`: array of flagged keywords

## Test Plan

### Unit Tests

1. **Test metadata-only event acceptance**
   - POST SMS event with sender/recipient/timestamp → 200 OK
   - Verify event stored and encrypted

2. **Test content field rejection**
   - POST SMS event with `content` field → 400 Bad Request
   - Verify error message: "SMS events must be metadata-only in v1"
   - Verify event NOT stored

3. **Test feature flag enforcement**
   - Verify `EnableMessageContentCapture` defaults to `false`
   - Verify no code path enables it without explicit configuration change

### Integration Tests

1. Companion app sends batch of SMS metadata events → ingestion succeeds
2. Companion app attempts to send SMS content → ingestion rejects
3. Alert rule evaluates metadata-only SMS event (unknown contact) → alert fires

## Migration Path to v2 (Content Capture)

When VE-001 legal sign-off is obtained for a jurisdiction:

1. Update `FeatureFlags.EnableMessageContentCapture` for that region
2. Update Event schema to add optional `content_encrypted` field (backwards-compatible)
3. Update ingestion validation to allow content when flag is enabled
4. Update alert rules to support keyword matching
5. Update companion app to collect content (with separate permission grant + disclosure)
6. Update dashboard to display content-based alerts

**Critical:** Content capture must be:
- Jurisdiction-specific (feature flag per region)
- Separately disclosed to guardian during setup
- Separately disclosed on child device (indicator update)
