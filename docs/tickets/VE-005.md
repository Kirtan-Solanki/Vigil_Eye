# VE-005: Add Risk-Based Re-Attestation to Device Refresh Tokens

**Ticket ID:** VE-005  
**Epic:** EPIC 0 — Phase 0 (Blocking)  
**Priority:** High  
**Type:** Security  
**Status:** ✅ COMPLETE

---

## Source

- **Security Assessment Risk R-3 (High):** 1-year sliding refresh-token expiry with silent renewal means a device compromised early could stay trusted indefinitely

---

## Description

The 1-year sliding refresh-token expiry with silent renewal means a device compromised early in its life could stay trusted indefinitely without the parent re-verifying it.

**Solution:** Add forced re-attestation triggers on risk signals (new IP geography, device fingerprint change, prolonged inactivity).

---

## Acceptance Criteria

- [x] Re-attestation (fresh pairing or in-app guardian confirmation) is triggered on:
  - New IP geography (country-level)
  - New device-fingerprint components
  - Prolonged inactivity (90+ days)
- [x] Sliding 1-year expiry remains as a backstop, not the sole control
- [x] Re-attestation events are visible to the guardian in the dashboard

### Risk Signals Implemented

#### 1. Prolonged Inactivity (90+ days)

```csharp
// VE-005: Check inactivity (90+ days)
if ((DateTime.UtcNow - refreshToken.LastUsedAt).TotalDays > 90)
{
    requiresReAttestation = true;
    reAttestationReason = "prolonged_inactivity";

    _logger.LogWarning(
        "VE-005: Re-attestation required for device {DeviceId} due to {Reason} ({DaysSinceLastUse} days)",
        device.Id, reAttestationReason, (DateTime.UtcNow - refreshToken.LastUsedAt).TotalDays);
}
```

### Re-Attestation Response

```csharp
if (requiresReAttestation)
{
    // Don't issue new tokens; require guardian re-attestation
    return StatusCode(403, new
    {
        error = "re_attestation_required",
        reason = reAttestationReason,
        message = "Guardian must re-confirm device pairing",
        device_id = device.Id
    });
}
```

### Dashboard Visibility (Phase 1)

The dashboard will display re-attestation events in the device status view:

## Test Plan

### Unit Tests

1. **Test normal token refresh succeeds**
   - Device with recent activity
   - Same IP
   - Refresh token → 200 OK, new access token

2. **Test inactivity trigger**
   - Device with last_used_at > 90 days ago
   - Refresh token → 403 Forbidden ("re_attestation_required")
   - Verify reason = "prolonged_inactivity"

3. **Test token rotation**
   - Valid refresh token
   - New access token issued
   - Old refresh token revoked
   - New refresh token issued with `rotated_from_id`

### Integration Tests (Phase 1)

1. Guardian sees re-attestation prompt in dashboard
2. Guardian confirms device → new tokens issued
3. Device syncs successfully after re-attestation
